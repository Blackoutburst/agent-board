# Explicit inactive message-target append

Board 2.17.0 uses schema17 and exposes 70 MCP tools. Adapter 0.31.0 adds the
finite `messages_append_v1` path to its acquired owner worker. Completion records
one inactive message target; connection, model catalogue and model access remain
`not_attested`. The source change starts no model, feed, login or service.

## Prerequisites

The Unix owner must already have a compatible protected release installed, the
explicit C0 source catalogue replacement completed, and the exact personal Codex
slot paired and prepared in the owner's fixed private slot directory. Board data
never supplies a path, command, instruction or credential for that preparation.
The protected source checks and existing two-child recovery guard remain strict.
Installing this Board release does not perform these owner-side steps.

Every old active instance must have a complete real human Stop with matching
generation and launch identity. Preserve those identities, rows, launch hashes
and Stop commands. A different Stop remains valid safety control and invalidates
the append's old CAS; it does not silently produce a replacement proof.

## Operation

The human API under `/api/server-hosts/{host_id}/messages-append` provides a
separate grant, bounded context, request/history and cancellation. Cancellation
is possible only while the request is `requested`. The older
`metadata_request_only_v1` A draft stays inert and cannot be promoted to B. A and
B exclude each other before any historical receipt replay.

The manager uses six closed tools:

- `poll_server_messages_appends`
- `prepare_server_messages_append`
- `precommit_server_messages_append`
- `commit_server_messages_append`
- `complete_server_messages_append`
- `report_server_messages_append_status`

The first four mutations return the exact 23-field phase proof directly.
Request, owner/device, grant, profile/version and personal slot remain correlated
and freshly checked at each positive boundary, including receipt replay.
Private hashes are declared data; Board does not attest private application.

The actual worker holds its owner acquisition and real child leases, advances
one finite phase, and performs RPC outside its mutex and SQLite transactions.
Pending B suspends admissions, ticks, feeds, Start/Restart, ordinary publication,
replacement and reassociation. The current device channel still delivers,
acknowledges, applies and reports real Stops. A refused or uncertain append can
report only a closed blocked reason, independently of phase and cleanup.
This is a retained historical signal for that request revision, not a live health
observation. In particular, an exact successful phase5 receipt replay does not
erase it or establish that local recovery completed. The interface labels it as
the last error received; current instance observations remain separate.

Cold recovery keeps the original intent and exact request keys. A retained
complete reply is checked against fresh catalogue membership before the local
completion. A disabled prepared snapshot is preserved; active or uncertain state
stops safely and requires reconciliation. No old model activation is replayed.

Completion adds one member with desired `stopped`, observed `unknown`, cleanup
false and no Start command. Later activation requires its own existing controls
and observations. After the first complete B, ordinary publication cannot add,
remove or rebind members behind this operation.

## Release and limits

Schema16-to17 migration is transactional and preserves existing A requests,
barriers, admissions and history. Retain schema17, both request histories,
proofs/statuses and private journals for rollback; use compatible corrective
source. Never restore an older database or reinterpret a stored hash as authority.

Local synthetic tests do not qualify a live provider account or installed owner
release. Linux 3.10 qualification, complete release inventory and any deployment
remain separate explicit steps. The installed protected SDK0.30.5/release R74c365
is not upgraded or restarted by this source work.

The intended cloud product still requires a hierarchical team of managers,
coders, reviewers and writers, real task assignment and parallel execution.
This append path supplies a reliability prerequisite; it does not deliver or
activate that team.
