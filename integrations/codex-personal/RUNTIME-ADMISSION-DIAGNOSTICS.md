# Runtime admission diagnostics

Runtime failure metadata describes a refusal; it grants no admission, cleanup,
replay or publication authority. The existing status and uncertainty remain
unchanged. A missing Runtime reservation is not a durable negative receipt.

The Runtime channel keeps the worker's original registration. Refreshing a
changed profile would defeat cancellation. The MCP error parser accepts only
the exact known tool prefix and a finite set of public codes; arbitrary remote
prose, paths, provider diagnostics and credentials never enter this metadata.
The blocked turn records a closed `stage`/`code` pair. A failed review may carry
the same pair into its private queue receipt and the service's public status.
The pending service can read that pair again without another model or RPC.

Review remains separate from coding. The controller must already own the live
claim and supply a protected callback that freshly checks the exact sealed
commit, scope, material and independent read-only export. Selection hashes and
historical test evidence are data, never current author authority. The worker
has no Git, claim acquisition, ticket mutation, shell, merge or publication
capability. Its durable opinion remains private until the lifecycle validates
the same delivery and current authority for deliberate publication.

The server continuously checks the original review scope and permission epochs.
A finished cleanup receipt proves neither current review authority nor a merge
on today's target branch. Reauthorizing a completed review uses the exact old
reservation and server pin, without another inference. Reopening a driver
requires the same concrete source; it never resumes an author worker.

Before service publication or queue acknowledgement, cleanup must still pass
the existing fresh driver verification. Failed results and uncertain cleanup
remain distinct failures. Diagnostics cannot bypass either guard, release a
claim, consume a queue task or repair an old journal.
